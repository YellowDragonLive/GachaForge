# 项目长期约定 · 抽卡工作台（X:/image）

## 交互 / UI
- **抽象概念优先用缩略图呈现，但必须按需悬浮**（用户 2026-11-15：「缩略图能帮人类快速判断抽象概念」；后续修正：「缩略图应该是按需悬浮而不是全部打印出来」「每个概念其实只要一个缩略图，点击概念进入一个页面看到全部曾经出过的图片(limit50)」）。列表页默认零 `<img>`，hover / focus 才浮出**一张**代表图；点概念名进详情页看最多 50 张。语义卡、概念墙、结果槽位 chip 全走同一套按需机制。缩略图同时是更快的选择控件，不只是装饰。
- **缩略图是通用呈现层，主数据源是抽卡数据库自己**（用户 2026-11-15：「缩略图可以推广到其它抽象领域，抽卡的时候已经有数据库了」）。v2 关系链：`draw_slots/draw_slot_tags → image_assets → images.thumb_path`，加上 `draw_profiles/session_loras` 里的 checkpoint/LoRA；物化到 `concepts/concept_images`。每次抽卡把「概念 + 它生成的真实图」存全，任何概念都能反查代表图，随使用自生长。外部 1025 张画师风格样图只作冷启动补充，不搬 3.2GB 原图、不常驻服务。`images.rating` / `favorite` 决定封面分（`rating×2 + favorite×5 + 新鲜度`），是最终人工信号。
- 凡是后端能枚举的值一律点选（下拉 / chip），不让用户手写表达式或 JSON；手写只作为 `<details>` 高级逃生口。自然语言描述（如「想要的感觉」）是 AI 交互入口，不在此限，但要给预设 chip 减少打字。
- 过滤类功能必须让「被过滤掉的东西」可见（warnings + 空槽位标记），否则用户只能看到结果莫名变少。
- **UI/UE 必须从「用户使用路径」倒推，目标是路径最短**（用户 2026-11-16 批评上版左右分栏「没考虑 UE」：「应该把用户的使用路径考虑进去，然后调整 ui，使得用户使用路径最小」，并要求先列路径再设计）。判据是完成一件事的**步数与跨页跳转次数**，不是版式好不好看。页面按任务组织、不按功能组织；反馈内联、跳页归零；低频配置就地化。**一次只调版式不算 UE 优化**。2026-11-16 已按此重构：核心路径「抽卡→看到图」10 步 3 跳 → 3 步 0 跳。
- **抽卡台左栏 = 人物状态栏（游戏化），人数是人物卡的张数，不是开关**（用户 2026-11-16：「多人可以变成配置多个单人，这样就不会乱」「拆分成 场景 人物」「你要模仿游戏的人物状态栏 / 任务卡片，把抽卡做出很像游戏的界面」）。0 张 = 无人（`no humans`）、N 张 = N 人，永不出现「选了多人却只有一套配置」的矛盾。三态靠状态灯区分：灰点随机 / 蓝点蓝底锁定 / 空心点关闭。**人数被焊死在角色条目里**（15193 个角色有 6406 条自带 `1girl`，`2girls` 仅 1 条），必须由面板统一写 `count_tags` 并把条目自带的计数 tag 剥掉，否则多人同框永远画成一个人。装配有内容时**忽略配方与全局过滤**（同开会互相筛空，最难排查），原配方收进「改用配方抽卡」折叠区。装备格默认关：物品类 69 个池混着食物厨具，随机只会拉低质量。
- **抽象的东西要画成形状，位置本身就是说明**（用户 2026-11-16：「左侧应该有个虚线人物，然后类似游戏一样会有 物品(prompt) → 人物部位，场景也应该类似」）。一行字看不出「发型」管的是哪儿，所以人物卡改成纸娃娃：**角色铭牌在头顶 / 左列发型·衣着 / 中间虚线小人 / 右列表情·装备 / 脚下一条动作**，左列右列各一条 6px 虚线连到身上；三态直接画在身上（虚线随机、实线加蓝底锁定、关闭只留 `.doll-body` 底稿，保证关掉几格时身体还完整）。场景同理：点画面=背景、点右下三色点=画风、点画框=构图。**部位点击用 `data-act="asm-open" data-key` 复用同一套事件**，不另写处理器；格 ↔ 部位的双向高亮用纯 CSS `:has()`，零 JS。0 张卡的空状态也要摆一具不可点的占位小人。
- **点部位看到的池必须是「匹配过的」，不是整类摊平**（用户 2026-11-16：「把后端的池在前端匹配选择可选，点了小人的衣着就有几个池子对应可选」）。568 个池按 kind 分 15 类，但同类里混得杂：「风格」19 池有 12 个是乐器，「物品」69 池几乎全是食物和花。所以 `rankPools/poolScore`（widgets.js）给每个部位配两级关键词（strong 正主 / weak 沾边），命中抬分；`POOL_OFF_TOPIC`（sex_/audio_/food_/flower_/nudity_）即使命中关键词也压下去；`POOL_CURATED`（人物-/组合预设//构图-）微加 8 分；条目数只做 log 微调（≤28）。**禁用池（enabled===false）不进推荐**。选择器 = 一行可点 chip（全部 + 前 8 个，带条目数，横滑）+ 完整池下拉兜底；**打开即落在匹配度最高的池**，选中池即使排 8 名外也提到行首（否则用户看不出自己在哪池）。
- **「全部」不能等于「按 id 前 N 条」**：条目按池导入，前 60 条会全来自同一池（实测点衣着 7 条全是「人物-女性时尚穿搭」）。`list_items` 在没指定池时用窗口函数每池取 3 条（`cap//20`，≥2）再按池大小降序，60 条盖住 20 个池；前端按 rankPools 顺序排组并渲染**可点组头**（点 = 只看这一池）。单池模式条目行不再重复写池名，宽度让给条目名。
- **状态栏立绘是「按需悬浮」的唯一例外：常驻一张，因为要和出的图直接对照**。立绘来自该角色的概念封面（数据库里它出过的图），所以必须走条目的**英文 `tags`** 推 key（`1girl, artoria pendragon \(fate\)` → 剥掉人数取第一个 → 去反斜杠小写），**不能用中文 `label`**——`label` 是「艾比蓋兒·威廉斯 (旅行服)」，拿去匹配概念 key 永远查不到。立绘现在**铺在小人底下当底图**（`.doll-art` 是整块按钮，点空白/照片进概念详情页），有图时描边转白色加 drop-shadow，照片上仍能看出哪块是哪块；没出过图的新角色只有线稿小人，生图成功后要清 `state.portraits` 缓存让它长出来。
- **一抽 = 一张任务卡**：编号徽标 + 状态徽标（待生成/排队/生成中 x%/已完成/失败）+ 顶部渐变条 + 条纹滚动进度条，卡头徽标、渐变条、编号由同一状态驱动；下半「本抽装配」把**锁定槽位标「锁」并高亮**，这是和右栏那张图逐项核对的地方。状态变化只刷 `[data-state-for]` 与 `[data-flag-for]`，不重建整张卡（否则 prompt textarea 会失焦、滚动位置丢失）。

## 架构
- 前端零框架、零构建（原生 ESM，`widgets.js` 零 import 纯函数层）；后端 FastAPI + SQLite；一条 `scripts/start.bat` 起全套，不新增常驻服务。
- 本地 AI 能力优先：能用本机已有权重/节点就不联网、不装云端 SDK、不要 API key。ComfyUI `:8188` 是现成的本地推理后端。
- 语义抽卡采用「构建期离线预算向量 + 运行期只做 numpy 余弦」：索引存 `data/semantics/`，可重建、不入库；模型权重存 `data/models/`，两者都不进 git。运行时缺依赖要优雅降级，不能拖垮其他功能。
- **v2 彻底规范化是单一事实源**（用户 2026-11-15 选方案 C）：`draw_slots/draw_slot_tags`、`draw_profiles/session_loras/session_recipes`、`image_assets`、`concepts/concept_images` 取代 `detail_json/meta_json/*_snapshot_json`。Alembic 基线 `0001_v2_relational` 重做，旧库只读归档不提供升级路径。对外 API 响应形状保持 v1 兼容（降低回归面）。概念粒度取结构化槽位 tag，不再切整段 prompt；出图落库增量维护索引，`rebuild_concepts.py` 可全量重建。
- **清空重建固定走 `scripts/reset_db.py`**：先 `--dry-run` 看清单；备份 → 旧库与 162 个图片文件**移动**到 `data/archive/<时间戳>/`（不物理删、可回滚）→ 新库重建字典 → **回迁用户配置**（checkpoint/LoRA/自建配方按名字）。清库不删配置是硬要求，否则真实模式 checkpoint 为空会出图失败。
- **依赖也不重新下载**（用户 2026-11-15 明确：「你别重新下载依赖，你直接剪切到这个文件夹就行」）。本机已有的 Python 包 / 模型权重一律直接搬进项目：`scripts/vendor_deps.py` 从本机 `.venv` 的 site-packages 搬到 `vendor/pydeps/`（需 Python ABI 一致，本机都是 3.13/cp313），`embed.prepare_model()` 把 Chroma 缓存的 ONNX 权重**剪切**进 `data/models/minilm/`（不复制两份）。不 `pip install`、不改 requirements 触发下载、`start.bat` 缺依赖只提示手动装一次。模型与包都不进 git、可重建。

## 工程
- 代码改动落盘即 `git commit`，中文提交信息（改了什么 / 为什么改 / 怎么验证）；多个独立改动拆多个 commit。
- 高频操作先写 `scripts/` 脚本 + `docs/运维_*.md` 手册，手册是唯一口径，流程变了改手册和脚本。
- 冒烟测试必须用 `%TEMP%` 临时库副本隔离，绝不污染正式库；验证数据按 id 精确清理。
- **部分更新接口是整体覆盖语义，必须带回原字段**：`upsert_recipe` 里 `row.gen_profile_id = data.get("gen_profile_id")`、`upsert_profile` 里 `row.loras_json = _dump(data.get("loras", []))`，只传改动字段会把配方关联的预设 / 用户 LoRA 清空。凡「就地改配方 / 就地调参」都要带 `gen_profile_id`、`loras`、`workflow`（2026-11-16 实测）。
- **同一台机器有多个 Python，启动脚本不能假设 PATH 里那个装了依赖**（2026-11-15 双击实测踩坑）：双击 bat 走系统 PATH 的 `X:\ProgramData\miniconda3\python.exe` 3.13.13（只有 httpx），终端走 WorkBuddy 自带 `C:\Users\13410\.workbuddy\binaries\python\versions\3.13.12\python.exe` 3.13.14（核心依赖都在这）。`start.bat` 按 `GACHA_PYTHON` → 项目 `.venv` → PATH `python` → WorkBuddy 版本目录的顺序探测「能 import 七个核心模块」的解释器，存 `%PY%` 全程复用并打印。不要给 miniconda 装依赖、不要自动 pip。验证双击场景要用「PATH 只含 miniconda」的临时 bat 干跑，别靠终端环境想当然。
