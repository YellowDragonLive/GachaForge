## 配方槽位消失 / 按池过滤语义修复 · 已完成（同日，用户实测反馈）

- **现象**：配方 #2 配了「画师 / action / 角色」三槽位，抽出来只剩 `fixed_head` + 角色。查会话 #36 的 `recipe_snapshot_json`，三槽位完整 → 是运行时被过滤掉，不是配方被改。
- **根因（重要）**：`apply_filter_spec()` 把**裸关键字当全局条件**，作用于每一个池并**丢弃空池**。隔离库复现：`filter=''` → 558 池 / 三槽位全在；`角色:fate` → 552 池 / 三槽位全在；裸 `fate` → 4~5 池 / 只剩角色；`run_recipe()` 对空槽位不写 detail，所以界面完全静默。用户表单里填了裸 `fate`，而配方槽位 JSON 里角色槽位本已写了 `"filter": "fate"`，属于重复且危险的叠加。
- **附带缺陷**：`filter_pool()` 大小写敏感，UI 示例写 `角色:Fate`、条目多为小写 `fate`，照示例填会 409「过滤后没有任何可用条目」。已改大小写不敏感。
- **正确写法口径**：`池名:关键字` = 只筛该池；裸关键字 = 筛全部池；用配方时优先在槽位 JSON 写 `filter`，表单过滤留空。
- **修复**：`run_recipe()` 为空槽位写 `{empty, reason}` → 前端「⚠ 无匹配条目」chip；`create_session()` 返回 `warnings`（移除多少池、哪些槽位空了）→ 结果区常驻黄色告警 + 输入时即时提示；`state.form` 也存 `sessionStorage`，刷新后表单不再回默认。
- **验收**：冒烟 31 → **36/36**，前端契约 10 → **11/11**；真实服务实测裸 `fate` 返回 2 条告警 + action 空槽位标记，`角色:FATE` 200 且四槽位齐全。验证会话按 id 精确删除，用户数据未动（期间用户持续抽卡，库从 36/106 涨到 96/286，说明页面已能连续用）。
- **通用教训**：**过滤类功能必须让"被过滤掉的东西"可见**，否则用户只能看到结果莫名变少；界面示例字符串必须与实际匹配语义（大小写）一致。

## 两层过滤冲突 / 表单优先 · 已完成（同日，用户追问 `角色:asuna`）

- **现象**：表单填 `角色:asuna` 仍抽不到 asuna。库里其实有 **18 条** asuna 条目（`zh_TW` / `wai_characters` / 词卡池），写法没错。
- **根因**：配方 #2 的「角色」槽位写死 `"filter": "fate"`，表单先筛 asuna、槽位再筛 fate，两层 AND → asuna 条目全不含 fate → 角色槽位空。隔离库四组合复现确认。
- **设计决策（重要口径）**：**会话级表单过滤优先于配方槽位 filter**。表单非空时只 `copy.deepcopy` 本次执行的 `recipe_def`、清空槽位 filter，写进 `warnings` 说明覆盖了什么；**数据库里的配方不动**，快照记录覆盖后的实际定义以保证可复现。表单留空则槽位 filter 照常生效。
- **顺带**：用户后来自己把配方 #2 改成 v4（三槽位 filter 全空），所以生产验证时覆盖告警没触发；改用内联带 fate 的配方才验到告警。排查时**别假设用户配置没变，先读库里当前定义**。

- **教训**：当同一维度存在"配置文件里的固定条件"和"界面上的临时条件"时，必须明确优先级并让覆盖可见，否则用户改了界面却以为没生效。
